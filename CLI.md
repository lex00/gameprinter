# The gp commands

Generated from gp's own commands by `gp self docs`; `just check` fails if it differs. Edit the commands, not this file.

## The public set

For making and playing games: what a person installing gp uses.

| Command | What it does |
|---|---|
| `gp assets find` | Find a game's assets in any dump of it: another header, revision, region or re-release, at any offset in any bank. Each template of the game (its `template.game`) is compared by the content its asset map holds (gp assets hash), the model is picked by the program found, and each asset is reported found unchanged (where), found with small changes (where and how much) or missing. A ROM the ROM no game's roms.toml knows gets a draft entry (docs/sources.md) |
| `gp assets hash` | Write each span's content into the ROM's asset map: its BLAKE3, its length and a fingerprint of each 16 bytes (hashes, not ROM data), after the map's last asset. `gp assets find` finds the spans in other dumps by it (docs/assets.md, "Content") |
| `gp assets lift` | Decode a ROM's assets into files: tiles as indexed PNG, palettes, metatiles, levels, tables, text and pointer tables as TOML, object lists and music as directories of TOML files, plus the asset map as assets.toml. The map is the one for the ROM's hash in $GP_ASSETS, or in the tool repo's and each game's assets/, unless one is given |
| `gp assets open` | Edit an entity's sprite set in an external pixel editor (docs/sprite-editing.md). It writes the set in the image config's layout and starts the editor if it's installed (Pixelorama first; nothing is downloaded), then brings each save back through every edit check as a proposal in the copy's history (or placed, with `--place`) |
| `gp assets pack` | Encode a lifted directory back into ROM bytes and compare them with a ROM: the round-trip check, which exits 1 naming each asset and offset that differs. Nothing is written |
| `gp assets stub` | Copy a lifted directory with every presentation slot of a model replaced by a placeholder of the same shape (licensed CC0-1.0) and the slots the simulation reads unchanged, record each slot's status and provenance in slots.toml, and with `--json` print the slot catalog (docs/stubs.md has the details) |
| `gp corpus bump` | The next version from the clips' changes since the version corpus.toml records. A clip added is minor; a clip removed, a recipe changed, or another ROM or mapping is major; metadata only is a patch. A plan's clips are compared with the plan git has at HEAD. `--write` records it with a changelog entry |
| `gp corpus diff` | The clips added, removed and changed from corpus A to corpus B, and the version step that makes. Each is a folder, or REV:DIR for a folder as git revision REV has it (`HEAD~1:games/donkey-kong`) |
| `gp corpus import` | Turn GAME's mechanic sessions ($GP_HOME/mechanics/GAME) into the clips of its corpus plan: every clip of every session, as its presses from power-on to its start and its own, in inputs/. Sealed sessions stay out, and so do clips whose inputs are a sealed run's ($GP_HOME/sealed/GAME). Rows out of scope in the quest log stay out too, as does what the plan's [import] excludes. Prints what changed and the version step; `--write` writes the clips and records the version |
| `gp corpus init` | Write corpus.toml beside DIR/clips.toml, so an older clip set becomes a scoring corpus with a name, a version (1.0.0 unless given), the ROM and mapping from the set and the content hash of its recipes. A game started by `gp game new` has a corpus plan already |
| `gp corpus reduce` | Propose the fewest clips of a game's corpus that still run every routine and branch way the corpus runs, each counted by stage (the stage byte the mapping names). Each clip's own frames are counted as `gp code listing` counts them (on a romset, as `gp reach --window` does) and, for the NES, kept in the events store. Guards (the first clip each fix commit of the model, mapping and hooks names, and `--keep`) stay; then the greedy multi-cover by frames, and a reverse pass. Prints the kept set by stage and family, the clips any cover needs, the exact duplicates and the untaken branch ways by stage. A plan only: `--write PLAN` writes it outside the repo, and the clips are never changed |
| `gp corpus score` | Score a game's corpus on a model: every clip made again from the ROM, played through the model and checked against its curve. Prints the clips exact and the fidelity and, with --json, the score record |
| `gp corpus show` | A corpus's name, version and hash, whether its clips changed since that version, and, for a template, the corpus it is scored against and its score records, each with the corpus it is from |
| `gp corpus verify` | Check the corpus's content hash, then make every clip again from the ROM through the game's module into run RUN (as `gp corpus score` does) and check every curve hash; a plan's curves are derived, so each of its clips is only made. Exit 1 on any difference |
| `gp game attest` | Attest a published version of a game: derivation, module build and score, as signed statements under attest/<id>/ in the registry. Takes a clean `gp game score` output of the package |
| `gp game build` | Build a game's module from its package folder and the kit, in a sandbox that reads nothing else and has no network. Exits 1 when the hook crate breaks the rules, 2 when the build fails. With no `--kit` and no `-o`, the module is built from this gp's own kit into $GP_HOME/work/modules (or reused from there), as every tool that opens the model does, and its path printed |
| `gp game fetch` | Fetch NAME@VERSION by id into a folder, checking every signature (with --root) and hash, and lift every ROM entry it finds in the ROM folder |
| `gp game hash` | Print a built module's BLAKE3 hash |
| `gp game kit` | Write the module kit: the tool's sources for a game module and the crates they need, ready for a build with no network |
| `gp game new` | Port a game from a ROM you own that no game names yet: its folder (a template) in the games checkout, with a model skeleton for the genre, the ROM's hashes in roms.toml, pins that hold, and no clips. Writes over nothing |
| `gp game score` | Score a game from its package and the ROM alone, in this $GP_HOME: every clip and curve derived from the corpus plan and the ROM, played through the module, and the score record written to FILE. Exits 1 when the corpus has problems |
| `gp game test` | Run a game's hook crate tests as `gp game build` builds it: in a copy of the kit's tree under $GP_HOME/work/module-build, in the sandbox, offline, with the package's lock, for this machine. Nothing is written in the package folder (no ext/Cargo.lock, no target). Exits 1 when a test fails, with cargo's last lines |
| `gp model blind` | A model and a state mapping from the ROM alone, by playing it. Blind discovery finds the player and its buttons. Then runs of the game measure the player's speeds, jump and size. Facts are `observed`, each with the frames it came from (crates/gp-cli/src/model_blind.rs) |
| `gp model check` | Check a model directory: model.toml against the schema (references, roles, events, extensions, evidence for every fact, each evidence ref's file and line, in the repo or package or in a pinned download under $GP_HOME/work, skipped with a notice when that isn't there), and fidelity.toml, if there is one, against the model. A profiles.toml beside it is checked too. Prints the facts by source. Exits 1 on any problem |
| `gp model derive` | Derive the model's hand-written facts from what their evidence cites (docs/derivation.md): the constant, immediate or data row a ref names in assembly source (evidence), the value the routine's code computes there by constant propagation (code), the table the line's label names lifted through the asset map, the asset slots against the map, and the generator scripts the evidence names rerun over the lifted assets (data, with `--assets`), and the feel parameters measured from recordings (recordings, with `--recording`). Each fact either agrees or differs, or is new or underivable (with the class that could derive it and why); a question goes into questions.toml where a derived value differs |
| `gp model diff` | List every fact that differs between two models, by model path. Exits 1 if any does |
| `gp model fmt` | Fail if the model or contract isn't in canonical form. Rewrite model.toml and fidelity.toml in their canonical form, the one text each model has. With `--check`, write nothing and exit 1 if either isn't in it |
| `gp model gate` | Hold a patch to a game in the games repo to its corpus: PASS or FAIL, and what passes lands |
| `gp model mechanics` | A model's mechanic catalog: every mechanic it uses, from the record the simulation's components and the model's hooks declare (system, parameters with types, units and ranges, reads and writes, events, assumptions, invariants, measures, the primitives it's built from, and for a hook the general mechanic it's like), the class of every model path (mechanic, parameter, content or presentation), the hooks that are still game-specific code, and the problems found by holding the model to the records (docs/mechanics.md). Exits 1 when the model and a record disagree |
| `gp model mutants` | Write the model's mutants (`[[mutant]]`): each number up by one (a fraction by a sixteenth) and each flag turned over (`constant`, or `period` for `period`, `every` and `after`), each transition deleted, each condition, `stops` entry and tile kind dropped (`input`), and each pair of adjacent systems swapped (`order`). Pictures and documentation are left alone |
| `gp model propose` | Measure the model's feel parameters from store recordings. gp track finds the player and the enemies, and their positions and the controller give the player's movement (walk and run speed, acceleration), its jump (speed, gravity, held gravity, fall limit and rise by hold time) and the enemies' steps, periods and speeds. Each is proposed as a fact by model path, compared with the model's own, and where the measurement can't decide, a question goes into the directory's `questions.toml` (docs/mechanics.md) |
| `gp model questions` | List the questions in a working copy's questions.toml, and answer them: an answer to a number's question is written into the model as a stated fact |
| `gp model refine` | Refine a working copy of a game's model against the original, clip by clip from its corpus, through the lockstep: the clips checked against the ROM first, numbers fitted from the original's state at each clip's start and written as facts with evidence, shape questions asked in questions.toml. Without --lockstep, the loop measures store recordings (--recording) as gp model propose does and runs gp validate between rounds: a measured fact a failing check backs is written, answered questions are written as stated facts, the rest asked |
| `gp model schema` | Print the JSON Schema of the format WHICH names. Print the JSON Schema of the format WHICH names. `gp self schemas` writes them all to schema/ (`just docs`) |
| `gp model static` | Stage 0, the static harvest, is every part of a model the ROM's code settles without running it, from the ROM and the asset map only (docs/plan-extraction-process.md). Elements from the code's dispatch and what each routine touches; constants, thresholds and periods; state machines from the bytes the code branches on and writes by constant; mapping rows; model facts, each with the instruction it comes from; and open facts with the routine and bytes that decide them. `--grade KEY` grades it against a game's answer key (games/mosshop/static-key.toml). On an arcade romset it reads the main Z80's code alone: routines and their roles, the interrupts, record tables, state machines, counters, timers, input and the random routine (docs/code-reading.md) |
| `gp package hooks` | Print the hash of a package folder's hook code |
| `gp package scan` | Sort every file and every field of a package folder into four buckets: ours, reference, from the ROM and needs rewrite. Compares with each ROM of its `[[rom.entry]]` found by hash in $GP_ROM_DIR and prints no ROM byte. With no ROM it says that nothing was compared. Exits 1 on any needs-rewrite item or a failed rebuild, or with --baseline only on a needs-rewrite item the baseline doesn't list |
| `gp registry check` | Test a registry from outside, against its root if --root is given |
| `gp registry init` | Make a registry in a folder or s3://BUCKET |
| `gp registry publish` | Publish a folder of files as one exact version |
| `gp registry reindex` | Rewrite the list files from these name@version entries, signed if --key is given |
| `gp registry serve` | Serve a folder registry and a built page on this machine only |
| `gp roms add` | Copy ROM files you own into $GP_ROM_DIR/nes/, or a romset (a MAME zip) into $GP_ROM_DIR/arcade/, identifying each one. A ROM no game names yet is added too, as unknown: `gp game new` starts a game for it |
| `gp roms clean` | Write a cleaned copy of a NES image: header from the game's roms.toml (or the file's, by the header rules), no trainer, no trailing bytes. Never changes the input. Exits 1 when the cleaned data matches no game's roms.toml |
| `gp roms diff` | Compare the PRG and CHR data of two NES images. Either side may be a raw PRG binary, such as a disassembly build |
| `gp roms scan` | Identify every NES image and arcade romset (a MAME zip) in $GP_ROM_DIR, whatever it's named, by the game whose roms.toml holds its hash, and report junk around an NES image's game data |
| `gp serve` | Game Printer's page, at http://127.0.0.1:7710/: a game's tabs CLIPS (record clips of the original, hand them to your agent, review them on the model), REFINE (the background work scoring and refining the model), PLAY (the model) and THEMES, with your agent's log beside them. gp mechanic start and watch open it |
| `gp template build` | Build the assets of a game made here (source.how = "authored") from its authored.toml: a data image that nothing plays (to $GP_HOME/work/images/), its asset map, and the lifted directory. Exits 1 when the asset map or template.toml's pins are stale, unless --write updates them |
| `gp template check` | Check a ROM against the template: accepted hash, map pin, lift pin |
| `gp template cites` | Index the ROM addresses ($8000 and up, written `$C46B` or `0xC46B`; on an arcade romset any inside the main CPU's program) that templates' model.toml, mapping.toml, probes.toml, delta.toml and hooks (the `[ext]` crate's sources, a derived template's base's) cite, each with its files and lines and the routine of the code map it is in, so a planner can see what is covered (docs/code-reading.md) |
| `gp template derive` | Make a derived template's files (template.toml's [derive]). They are the base template's per-game files (model, contract, state mapping and the rest), with its source renamed to this template's and the delta merged over them (docs/templates.md, "Derived templates"). Exits 1 when a file is stale; `--write` rewrites them |
| `gp template extract` | Turn a template into a copy filled from your own ROM: check the ROM's hash against the template's source declaration, lift its assets with the template's asset map, check the lifted files against the ROM byte for byte and against the pinned digest, copy the model, and check its slots against the lifted assets. Every hash goes in extract.toml beside the copy. Exits 1 when a check fails and 2 when no accepted ROM is found |
| `gp template font` | The font check (docs/templates.md, "The font check"): every character the model writes (HUD counters and text, level labels, screen text such as a turn screen's) has a glyph with ink, no two characters share a tile, every charset in the asset map agrees with the font's, and no other art draws a glyph's tile. Lists the font bank's free tiles, the only ones a generator may put a new glyph in. Exits 1 on any problem |
| `gp template pack` | Write an asset-free copy of a template, with its asset map inside, as a directory or, for an output ending in .zip, a zip archive with fixed timestamps (the same template always packs to the same bytes). Runs the asset-free checks first (gp package scan on a package folder, and the pins when an accepted ROM is found) and refuses a template that fails them |
| `gp template served` | Check that a game's folder, as it would be published, holds none of the original game's data: no line of 24 characters or more of its built files may be held by the original's lifted files, and none of its bytes or lifted files may be the ROM's. With --folder, the same for every file of a folder to be served. Exits 1 on any find, and 2 when a ROM isn't found |
| `gp theme check` | Check a model's theme stack: each theme's file, its restyles' slot names against every model in its `for` list (read from the templates of the same game), then the readability check and the Style checks on the themed art. Exits 1 when a theme is invalid or a restyle names a slot or entry no model has. It also exits 1 when the readability check refuses or a Style check fails. Without theme options it checks the model's own stack (`--themes`) |
| `gp theme fetch` | Fetch a published theme by the game's index: the manifest by its hash, its signature, and each file by its hash, from the local store or the first mirror that has it, every hash checked, into OUT (default $GP_HOME/themes/packages/GAME/THEME) |
| `gp theme fit` | Fit art to a game's slots (docs/theme-kit.md, "Fitting"). Each sprite slot's frames come from `ART/<slot id>/<frame>.png` (any size, any colors) or from the filled grids of `gp theme sheet` (--sheets, read through sheets.json). Each frame has its background cleared (alpha, the key color or a flood from the edges) and is cropped to the figure. One scale serves the whole slot. The frame is placed by the anchor, downscaled by area averaging, and cut into the game's tiles by one lightness split for the slot. Each picture slot (`ART/<slot id>.png`, or the sheets' picture) is kept whole. Needs the kit's local part (`gp theme kit --rom`). Merges into OUT's theme.toml when it has one |
| `gp theme generate` | Make a theme's art with Runway's API (docs/theme-kit.md, "Generating with Runway"). It makes the style board and turnarounds on gen4_image first. Then it makes each sheet of `gp theme sheet` on gpt_image_2, and every picture on gen4_image with those as references. Then it runs `gp theme fit` and `gp theme check --original`, makes single-cell calls for refused slots, and draws a contact sheet. Every call is in the run folder's ledger, so running it again continues without paying twice. `--dry-run` prints the calls and their cost and makes none; a paid run asks on the terminal or needs `--yes`, and stops before passing `--budget`. The key comes from RUNWAY_API_KEY, the keychain (service game-printer-runway) or $GP_HOME/secrets/runway (mode 600) |
| `gp theme kit` | Write a game's theme kit (docs/theme-kit.md) as kit.toml in the template's themes/kit/ (or OUT). For each art slot the kit gives its role and size. It also gives the slot's frames with their timing, and its colors and anchor. Its description of each slot names no character. For each sound role it gives the cue, length and loop. With --rom (checked against the template's accepted hashes) it also writes the local part, the tiles each frame is cut into and a reference sheet, under $GP_HOME/work/theme-kits/GAME/, never into the kit |
| `gp theme list` | List the themes published for a game. Each entry gives a theme's title, author and licence. Its size and package are given too, with the check results and whether the local store has the theme |
| `gp theme look check` | Check a large-art theme folder against a game, the way the page reads it: package.toml, look.txt and art.txt, every picture a rule names, the game's kit (every slot and pose drawn, nothing named the game lacks), how each picture sits on its body's box and feet row, names the kit denies, and ROM data (`gp template served`, when your ROM is here). Exits 0 with no problems (warnings allowed), else 1 |
| `gp theme look new` | Start a large-art theme for a game in a new folder: package.toml, theme/look.txt, theme/art.txt with one line per picture the game's kit lists (still to draw), a README and a .gitattributes. Writes nothing from a ROM, and refuses a folder that already holds files |
| `gp theme paint` | Paint a restyled-assets theme for a model from its roles: a sprite for each entity role and a cell for each tileset item role, in a paper-cutout style, as .pix files with a theme.toml naming them (CC0-1.0, origin generated). Writes OUT; refuses an OUT that exists unless `--force` |
| `gp theme publish` | Publish a theme version for a game (docs/theme-publishing.md). It refuses an id a theme the game ships with already has, runs every check (readability and Style, originality against the game's ROM when it is here, geometry), and refuses on any failure. Then it makes the package, scans it for game data and signs its manifest with a maintainer's SSH key. It keeps the package in the local store, copies it to the mirrors in mirrors.toml and adds it to the game's themes index, `themes/index/GAME.toml`, through the gate (GAME is the template's `game`, else its id). A game with no ROM art gets a look package (the theme, the look gp drew, the check results); a game lifted from a ROM gets a source package (the theme's own files and the check results, nothing drawn from the ROM's art). --dry-run stops before the store and prints what would be published |
| `gp theme recheck` | Check a published ROM theme (a source package) on a model of its `for` with a ROM on this machine, and add the result to the game's themes index: for a model the publisher had no ROM for, or to confirm one. Reads the package by its id from the local store or a mirror (every hash and the signature checked), runs the same checks as publish for the model, compares the look drawn here with the one recorded, and lands the index line with the model's result, slot fingerprint and look digest through the gate. A look that differs from the recorded one is reported and not added. The package and its signature are left as they are. --dry-run writes nothing |
| `gp theme schema` | Print the theme format's JSON Schema with `theme`, or the stack format's with `stack` |
| `gp theme sheet` | Write starting grids and prompts for an image model from a game's kit and a style card (docs/theme-kit.md, "Sheets"). Each grid holds a subject or a group of small slots. Its cells are sized by slot, and each has a label, a box and a line, with a neutral pose figure. The command writes a prompt file per grid for gpt_image_2 and for gen4_image (1000 characters at most); the style board and turnaround prompts to make first; a prompt per whole picture; and sheets.json, which `gp theme fit --sheets` reads back. OUT must be outside the repo |
| `gp theme style list` | List the style cards, personal and shared |
| `gp theme style new` | Write a style card with the look, the cast in your own words and palette hints. Shareable cards go to themes/styles/ in the repo and must name no game; --personal writes $GP_HOME/themes/styles/ |
| `gp theme style show` | Print a style card |
| `gp theme video` | Run a model in the interpreter on an input and write its frames, drawn with a theme stack, as an animated PNG. Prints the digest of the per-frame state hashes, which is `gp interp run`'s for the same input with any theme: the presentation reads the world and never writes it |

## The lab set

For research, tests and the workflow's own tools: what an agent or a contributor uses. May change without notice.

| Command | What it does |
|---|---|
| `gp agent approve` | Keep an attempt (what the page's keep does): marks it approved and writes it to $GP_HOME/work/agents/approved.json for the driver |
| `gp agent attempt` | Record an attempt at a clip: with `--worktree`, builds that worktree's gp and trial preview, scores the clip and every active clip with them, and records the score before and after, the clips better and worse, the preview and the commit |
| `gp agent bench` | The loop's efficiency in one table (docs/agents.md, "Loop efficiency") covers rounds and fixes per hour by source, and seconds per round with LLM calls per fix. It also gives exact and fidelity over a window, and is read-only |
| `gp agent brief` | Everything an agent needs to start on a clip, in one call: the clip, its first wrong frame and each wrong measure's values around it, and the mechanics that own those measures with their parameters. It also gives the code the evidence cites (file, line and routine), what the original's code read to write the first wrong measure (the Z80's on an arcade game), the open questions and the person's tells, with the attempts so far and the next commands written out in full. It is read-only and, with `--json`, has a fixed shape (`schema`) |
| `gp agent clips` | The run's active clips with their scores, those that don't match first. Read-only; the brief lists the first 20 |
| `gp agent done` | Say the work on a clip stopped, and why |
| `gp agent integrate` | Run by the coordinator, it picks the approved attempts not on main, in order, onto a new branch of this checkout, numbers the versions once, regenerates the schema, writes the attempts' CHANGE.md notes into the ROADMAP, and runs `gp model check` on the games. Stops at the first conflict. It doesn't merge into main or score: the tool gate lands the branch (docs/agents.md, "Merging attempts") |
| `gp agent note` | Post a progress note, shown on the clip's card and the REFINE tab. `--on` says in plain words what the work is on until another `--on` or done |
| `gp agent score` | Score every active clip of a run on a model folder with this build, as JSON: what an attempt reads from a worktree's gp |
| `gp agent state` | Who is working on what, and the attempts, in words |
| `gp agent tell` | Tell the agent something about a clip, as the person does from the clip. It goes to the inbox of the clip agent working on the clip, or waits for the next one |
| `gp agent tells` | The tells and their replies; `--open` for those without a reply |
| `gp author` | A prototype of the authoring API: a proposer edits a base template's mechanic parameters from a short request, gp's checks verify each proposal (schema, mechanics, the public tier, reach, a playthrough, difficulty against a target, the asked-for feel), the failures feed the next proposal, and one log row is written (docs/author.md). The proposer is scripted; only `--dry-run` is built |
| `gp baseline check` | Record each baseline into a temporary store and check its frame hashes, lag frames and RAM assertions. A baseline whose ROM isn't in $GP_ROM_DIR is skipped; our own test ROM is built in, so its baselines always run. Exits 1 if any check fails |
| `gp bench clips` | Grade the ROM-only clip tools on a game whose answer key is known (docs/benchmarks.md). The tools run in a home of their own (--work) on the hand-written model and mapping, over the game's corpus. Only the grader reads the answer key. The report holds the measures of docs/plan-extraction-process.md and the mutants each kind of wrong model leaves uncaught. Its hash leaves out the times, so a rerun gives the same hash |
| `gp bench report` | Print the measures tables of the last `gp bench scratch` and `gp bench clips` runs of a game, from their report.json files. Status reports quote this table (docs/plan-extraction-process.md, "Guards"). Exits 2 when neither report exists |
| `gp bench scratch` | Run every stage from scratch and grade it (docs/benchmarks.md). The start holds only the header the schema needs. Each stage's tools run on what the stage before left, and their output is graded against the real model and mapping. The report leads with the minutes of run time per second of gameplay played exactly. Stage 0 refuses a tool that reads the source or the labels. Each stage's output has a hash of its own, for telling which stage a change moved |
| `gp capture background` | The run's background queue (docs/show.md, "The background work"). It shows the queue's state, or scores clips here in the foreground. A job scores the next active clip not scored on the model as it stands. While the queue is on, `gp serve` does this work itself, and refines the working copy on the clip that drifts apart earliest |
| `gp capture carry` | What the game's clip starts can't carry into the rebuilt game (gp_interp::carry), for each start and, with `--every`, for frames sampled through the starts' presses. It lists every loaded object a start there can't carry and why, grouped by cause, with the starts each gap alone holds back |
| `gp capture dense` | Dense clips (docs/research/dense-clips.md) are a few short clips that each run much more of the original's code. Candidates from a coverage-guided search of presses at the game's clip starts, valued by the code, branches and measure values they reach on the original, chosen by greedy set cover. They are written as a clip set into a scratch folder (`--into`); the game read from is unchanged. The same seed, ROM and game give the same clips |
| `gp capture events` | Print a run's events after a sequence number, one JSON object a line, from the running `gp serve` |
| `gp capture fidelity` | The run's fidelity: `gp corpus score` on the run's game, every clip made again from the ROM and played through the model, with its fidelity line and record (game-printer's `capture fidelity`) |
| `gp capture impact` | What a change since an earlier score reaches (docs/gate.md, "Affected clips"), and how many of the run's clips it would score again by what each read. Scores none: `gp corpus score GAME --run RUN --reuse FILE --impact` |
| `gp capture list` | List the runs: every game of the games checkout, with the round and state of `gp serve`'s background work on it |
| `gp capture regenerate` | Make a game's kept clip set again from the ROM and check each clip's curve against the set's: `gp corpus score TEMPLATE --run RUN` (game-printer's `capture regenerate`). Exits 1 when a curve differs or a clip can't be made |
| `gp capture schema` | Print the event format's JSON Schema (`schema/capture-events.json`) |
| `gp capture verify` | Make every clip again from the ROM and check every curve hash: `gp corpus verify GAME --run RUN`. Exits 1 on any difference |
| `gp catalog` | The pattern library's finders on a template, beside what its model holds (docs/catalog-patterns.md). It lists each entity's patterns and whether they are components or hooks, and the asset map sorted by pattern. RAM slot arrays from the game's labels are set against the mapping's [slots] and, with `--recording`, tracked objects fitted to the behaviour patterns against the entities the mapping names |

| `gp sound fidelity` | Hold songs to the register log they came from: note onsets, pitch and volume per frame, and the two renders' loudness |
| `gp sound render` | Render a song, or a register log, to a WAV file through the APU synthesizer (or a sound bank mapping). An AY register log or AY songs play through the arcade board's sound (gp_arcade::sound) |
| `gp sprites capture` | Capture every sprite frame of every entity: the frames the game's sprite tables define (sprites.toml says where and in what shape) and every distinct frame the recordings show on each entity, merged into one sprite-set with each entity's clips by model state, their timing, palette variants and coverage. The set is written to the lifted assets; the model with its sprites is written beside it as a proposal, or over the template's with `--apply` |
| `gp sprites schema` | Print the schema of the image format config as JSON (`schema/image-config.json`) |
| `gp store gc` | Delete objects that no recording uses and that were unused at the previous `gc --yes` too (docs/recording.md). Without `--yes`, lists what it would delete and writes nothing. | `gp store put` | Add a file; prints its hash |
| `gp store reindex` | Read the recordings log and the manifests it names, and report what they hold. gameprinter keeps no index file (it reads the log each time), so this writes nothing |
| `gp store stats` | Object count and total size |
| `gp store unreferenced` | List objects that no recording in the recordings log uses, without deleting anything. Exits 2 if a manifest or log line can't be read, since the objects it names would then be listed wrongly |
| `gp store verify` | Re-hash every object and report any that changed |
| `gp testroms built` | List our own test programs, which are built rather than downloaded: each one's path under $GP_HOME/work/test-roms and the source in the repo it's built from, tab-separated. `just build-testroms` reads it |
| `gp testroms fetch` | Download every test ROM that's missing into $GP_HOME/work/test-roms, checking each against its pinned SHA-256. Exits 1 if a file's hash differs from its pin, 2 if a download failed |
| `gp testroms run` | Run the suites and report each ROM. Downloads missing ROMs first and skips, with a notice, any it can't get. Records each suite's pass count as `testroms.<suite>.passed` and `.total`. Exits 1 on a failure not listed as known in the manifest, a known failure that now passes, or a download whose SHA-256 isn't its pin. The suites are the NES's; an arcade board is held to MAME with `gp oracle diff` |
| `gp tool gate` | Hold a patch to gameprinter to the tool's checks and a Donkey Kong canary, and land it when it passes (docs/gate.md) |
| `gp trace diff` | Compare two recordings frame by frame and report the first frame whose state differs, with the fields that differ. Exits 1 if they differ |
| `gp trace fields` | Print the field table a recording's states follow: each field's name, kind and width, in order |
| `gp trace frame` | Print the state at one frame, by field. Read from the recording's trace, or by restoring a checkpoint and replaying when it has none |
| `gp trace instructions` | Print one line per CPU instruction over a window of frames, in the layout of nestest.log, by restoring the nearest checkpoint and replaying up to the window. An arcade recording prints both Z80s' instructions in time order, `M` the main CPU's and `S` the sound CPU's |
| `gp trace verify` | Check a recording's trace against its frame hashes. Exits 1 if a frame doesn't match |
| `gp track` | Find a recording's objects from its frame trace without a hand-written mapping: sprites followed from frame to frame, the RAM bytes that hold their positions, and a proposed `[slots]` section (docs/formats/tracks.md) |
| `gp validate` | Hold a model to its fidelity contract against recordings of the original (docs/validation.md): the contract's rules compiled into checks, each recording's input run on the original (read through the state mapping) and on the model, and compared. Exits 1 when a check fails, 2 when no recording could be run |
| `gp video` | Replay a recording with video rendering on and write it as an animated PNG with frame, input and event overlays (docs/video.md). Each frame is checked as it's drawn; exits 1 if one differs, unless another runtime made the run. An arcade recording draws the board's picture |
| `gp watch detail` | L3 for frames A..B (or A..=B) of a recipe the session ran, as `gp reach --detail` gives it |
| `gp watch events` | Print a session's events after `--after` (a `seq`), one JSON line each. With `--follow`, keep printing new ones as the writer adds them, until it is done |
| `gp watch explore` | Search again from the session's start clips (as `gp explore`, aimed at the stops left by default), writing into the session |
| `gp watch list` | List the sessions, with their ROM and how many events each has |
| `gp watch point` | What is under a box of the screen (`--rect X,Y,W,H` in picture pixels) at a frame of a recipe: the sprites there and the routine that last wrote each one's bytes in the sprite table |
| `gp watch rerun` | Run the session's recipes again watching addresses (`--watch $F0`) and hooking instructions (`--hook 01:8000`, `--hook sub_C1FB`), writing each write and call as `watch` and `hook` events (at most 200 for each in each recipe; the rest are counted) |
| `gp watch start` | Open a session and run stage 0 in it: read the ROM alone, run the start clips (stage 0's own starts, and `--start`'s), writing each frame's novelty (code, banks, edges, pointer values, stops passed) as it comes, read again with the runs, then search as `gp explore` does and write each clip it keeps with its novelty. The events go to $GP_HOME/watch/NAME/events.ndjson |
| `gp worker env` | Print a worker's setup. The setup is its private output folder ($GP_HOME/work/workers/NAME, made if missing), the cargo target folder of the worktree it runs in ($GP_HOME/work/target/BRANCH/HASH, HASH from the worktree's path; $GP_TARGET_DIR replaces $GP_HOME/work/target), the build profile (fastdev) and the gate's published gp ($GP_HOME/bin/gp), a nice level and a job limit from the machine's load and core count, and the rules every brief repeats. With `--shell`, the same as lines for `eval "$(gp worker env NAME --shell)"`: exports of GP_WORKER, GP_WORKER_OUT, CARGO_TARGET_DIR, GP_PROFILE, GP_BIN, GP (the gp the games repo's `just check` runs), CARGO_BUILD_JOBS and GP_JOBS, $GP_HOME/bin put first on PATH (so `gp` is the published build) unless `--rust`, a renice of the shell, and the rules as comments |
