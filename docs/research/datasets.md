# Data sets: recipes people can share and tables anyone can load

> `gp dataset export`, which this report built, and `gp roms add --patch`, which it leans on, were removed from `gp` on 2026-11-13, since Game Printer's target is a game that plays in a browser. The report is kept as it was written.

> In gameprinter (2026-11-12): `gp dataset export --run RUN --game DIR --out OUT` scores a game package's corpus (its corpus plan, `corpus.toml`) made again from the ROM into run RUN, as `gp corpus score` does, since gameprinter has no capture runs; `--module`, `--model`, `--assets` and `--rom` are `gp corpus score`'s. The code is `crates/gp-cli/src/dataset_export.rs`, with the shared Parquet and Croissant writers in `dataset_tables.rs`. The tables, the card and the record are as below; a clip's `start_input` is its start's presses file and `presses_log_blake3` its presses file's BLAKE3. On an arcade romset the frames count at the board's 30 a second. The rest of this page is game-printer's research report of 2026-10-30, kept as history: its runs, templates and Super Mario Bros. figures are that tool's.

The user, 2026-10-30: "we need to consider formatting and management of data sets here to ensure they are easily consumed by a modern audience". The goal it serves is the constant one: anyone can print a game with Game Printer from their own ROM, plus a patch for a hack. What is shared is recipes and derived data, never the game.

It reads against the clip set report (`clips.toml`, regenerating clips from a ROM), the NES hard-Mario report (base ROM plus patch), the difficulty report (label data sets), [the recording format](../formats/recording.md), [the state mapping](../formats/state-mapping.md), [profiles](../formats/profiles.md), [templates](../templates.md), [corpus](../corpus.md), [sources](../sources.md), determinism (results by key, the ledger) and positioning ("Port a whole community"). The dense clips report wasn't merged when this was written, so it isn't read here.

The prototype is `gp dataset export --run R --out DIR` (`crates/gp-cli/src/dataset_export.rs`). It adds one dependency, the `parquet` crate 60.1.0 with no default features, downloaded through cargo (section 13).

## Summary

| Question | Answer |
|---|---|
| Who uses the data | Six groups, and each needs something different: level designers want levels as text, hack communities a way in from their patches, runners frame-exact inputs and windows, ML researchers tables and an environment, rebuild projects curves to test against, and agents a fixed schema (section 1) |
| What to adopt | Parquet tables in a Hugging Face style repo with a dataset card and Croissant metadata, both generated by `gp`. Content hashes and the existing store for anything large. DVC, git-annex, OCI artifacts and Zarr aren't needed yet (section 2) |
| The sharing line | Shareable: recipes, inputs, hashes, scores, events, splits and difficulty windows. Local until decided, for a commercial game: per-frame measures read through the mapping from the game's RAM. Never: ROMs, frames, sprites, level data, snapshots, RAM or PPU dumps, sound. Gym Retro shipped more (savestates); the repo's rules are stricter, and the measures can be made again by anyone with the ROM (section 3) |
| Patches or source | Content made for Game Printer is a plain source repo: text that diffs, forks, pull requests and a license of the author's choosing. Only the base game's copyrighted parts come from the player's ROM at print time. A hack is imported once from base ROM plus patch, with its author's permission (section 4) |
| A repo layout spec | Yes. Bevy has no say in it: it's the engine the printed project uses, and its one convention is `assets/`. A Game Printer package is the template directory, versioned, with `clips.toml`, `levels/`, `evidence/` and `sources.toml` added, checked by `gp package check` (section 5) |
| Layers | The recipe (TOML in git), materialized data (made locally by `gp`, never shared) and derived tables (Parquet with a fixed schema, shareable within the line) (section 6) |
| Score records | Every score is a record of exactly what it tested, kept by model hash next to the model. The results key already holds most of it; missing are a portable build ID, the commit, the runtime, the profile, `clips.toml`'s hash and a patch hash. Signing later: an in-toto statement signed with an SSH key now, Sigstore when there's a hosted runner (section 8) |
| Built | `gp dataset export`: four Parquet tables (or CSV), a dataset card with the Hub's YAML, Croissant 1.0 metadata and a score record. ## 1. Who uses the data, and what each needs

| Audience | What they do | What they need | What Game Printer gives them |
|---|---|---|---|
| Modders and level designers | Make levels, art and small rule changes | Levels as files they can edit, diff and share; a quick way to play them; a difficulty read while they work | A package repo of text (section 5), `levels/` in the model's own format, `gp level difficulty` with its heat strip, printing from their own ROM |
| Hack communities (Kaizo, SMB Arena) | Play and make hard hacks of original ROMs; keep a catalogue | A path from the IPS patches they already have, credit for authors, the physics they trust | Base ROM plus patch import (nes-kaizo.md), the original's curves checked clip by clip, a package per hack with its author and license, and a card that says how exact it is |
| Speedrunners and TASers | Route, practise and verify tricks | Frame-exact inputs, frame windows per trick, movie import and export | Clips as presses from a start (TASVideos movies credited by URL and hash), the `windows` table, and the events table to line up tricks |
| ML and RL researchers | Train agents and world models, study difficulty | Tables in Parquet that load with one line, a fixed schema, splits, a deterministic environment, and frames they make themselves | The tables with a dataset card and Croissant, splits by level, a seeded deterministic rebuild to run agents in, and `gp video` for frames rendered locally from their ROM |
| Other rebuild projects (Remastered, decompilations) | Check their own engine against the original | The original's curves for a clip, in a form their tests can read | `measures` rows per clip and `curve_original` hashes; `gp compare remastered` already scores Super Mario Bros. Remastered on SMB1 clips |
| Agents driving Game Printer | Run the loop: score, refine, prune | A schema that doesn't change under them, JSON and Parquet they can query, the record of what was tested | The same tables, `record.json`, and `gp agent brief`'s JSON; DuckDB over Parquet answers "which measure fails most" in one query |

The ML group is the one with the most tooling expectations (Hugging Face, Croissant, Parquet). Meeting it costs little and serves the others too: a designer's level and a runner's windows are rows in the same tables.

## 2. Modern practice

| Practice | What it is | Fit for a recipe-first data set |
|---|---|---|
| Hugging Face dataset repos | A git repo whose `README.md` is the dataset card, with YAML that sets the license, tags and `configs` (each a subset with its `data_files` and splits). The viewer converts public data sets to Parquet on a `refs/convert/parquet` branch, in shards of about 500 MB, and asks for row groups of 100 to 300 MB uncompressed. `datasets` 4.0 no longer runs loading scripts, so a data set must be plain files | Yes. One config a table, Parquet files written by `gp`, no loading script. A recipe-only set is also fine there: TOML files and small tables |
| Croissant (MLCommons, 1.0, 2024-03-01) | JSON-LD on schema.org: a `sc:Dataset` with `conformsTo` `http://mlcommons.org/croissant/1.0`, `distribution` of FileObjects (with `contentUrl`, `encodingFormat`, `sha256`) and RecordSets of Fields (each with `dataType` and a `source` that extracts a column). The Hub generates Croissant for every data set it can convert to Parquet | Yes. `gp` writes `croissant.json` so a set has it before it's on the Hub, and with keys and descriptions the Hub can't infer |
| Datasheets for Datasets (Gebru et al., CACM, December 2021) | Questions a data set's makers answer: motivation, composition, collection, recommended uses | Yes, as the card's sections. The answers are mostly fixed for every Game Printer set (no people's data, no game data), so `gp` fills them in |
| Data Cards (Pushkarna, Zaldivar, Kjartansson, FAccT 2022) | Structured summaries of sources, collection and labeling, intended uses and ethics | The same role; the card template below borrows its "intended uses" and "known limits" |
| Frictionless Data Package (v2) | `datapackage.json` listing `resources`, each following the Data Resource spec, with Table Schemas | Close to Croissant in purpose. Croissant has the ML tools and the Hub; one descriptor is enough, so Croissant |
| DVC | A `.dvc` file in git with each output's `path`, `md5` and `size`; the data goes to a cache and is pushed to a remote | The idea already exists here: recordings live in `$GP_STORE` by hash and git holds the hash. No need for DVC on top |
| git-annex | "allows managing large files with git, without storing the file contents in git" | Same; not needed while the store does it |
| OCI artifacts (ORAS) | Push and pull non-container artifacts to OCI registries, told apart by `config.mediaType` | A possible later transport for packed templates; nothing in a data set needs a registry |
| Zarr | "chunked, compressed, N-dimensional arrays", specs v2 and v3 | Only if frames were shared as arrays. They aren't (section 3). A local world-model set could use it; not now |
| DuckDB | Queries Parquet in place, including from the Hub with `hf://datasets/<repo>/<file>.parquet` through `httpfs` | Yes, as the suggested way to query; nothing to build |
| Content hashes and semantic versions | A file is named or checked by its hash; a version says what changed | Already the repo's practice (BLAKE3 store, SHA-256 ROM identities, versioned formats). The data set gets a format version and a content ID (section 10) |
| Licenses for data | CC0 dedicates a work to the public domain. CC BY asks for credit. ODbL asks for credit, share-alike for adapted databases, and an open copy beside any restricted one | Section 11 |

What fits: Parquet tables, a card and Croissant, made by `gp` from recipes in git, with the heavy data made on the user's machine from their ROM. The large-file tools are answers to a problem the store already solves.

## 3. What may be shared

### Precedent

| Project | What it ships | What it leaves out |
|---|---|---|
| Gym Retro (OpenAI, MIT, archived on 2026-05-29) and Stable-Retro (Farama) | Per game: `data.json` ("the locations and formats of variables in memory"), `scenario.json` (reward and done), `metadata.json` (default start), `rom.sha` (No-Intro SHA-1 sums), and emulator savestates: `retro/data/stable/SuperMarioBros-Nes/` holds `Level1-1.state` to `Level8-1.state` | ROMs ("ROMs are not included and you must obtain them yourself"); `python3 -m retro.import` copies a ROM in when its checksum matches. A few non-commercial ROMs are bundled for tests |
| Arcade Learning Environment | From v0.9.0 the Atari ROMs are packaged in the PyPI install (release notes); AutoROM did it before, with an `--accept-license` flag | Not a precedent we can follow: it is a licence arrangement, not a recipe |
| TASVideos | Movie files (input logs) under CC BY 2.0, with credit, a link and a tool-assisted label (docs/open-questions.md, "Can imported TAS movies be redistributed?"). Hack runs need a publicly downloadable patch | ROMs |
| Data Crystal | RAM maps of commercial games, "released under the GNU Free Documentation License 1.2" | ROM data |
| SMB Arena | Hack pages with a base ROM name and an IPS patch, and an in-page patcher that applies it to the player's ROM (nes-kaizo.md) | ROMs |
| sm64 decompilation | The source; "A prior copy of the game is required to extract the assets" (`baserom.<VERSION>.z64`) | The assets |
| nukep's SMB-Vanilla | A C decompilation that "does not come with level data or graphical assets" and takes the player's files by SHA-1 (nes-kaizo.md) | Level data, graphics |

### The line

The repo has decided part of it already: traces and recordings of a commercial game are private, since RAM and PPU state can hold copied graphics, and anything published shares "only aggregate metrics and diff summaries with no memory contents" (docs/open-questions.md, M1.1). Snapshots are never committed (clip-set.md).

| Tier | What | Why |
|---|---|---|
| Shareable | ROM and patch hashes; model, mapping and contract hashes; clip recipes (start by recording hash and frame, presses as spans, frame count); TAS input logs with credit; the user's own presses; scores; first splits; body events ("the second goomba turns left at frame 40"); difficulty windows; curve hashes; metrics | Facts about play and our own text. None holds a byte of the game. Each matches a precedent above: TAS logs, RAM addresses, ROM hashes |
| Local until decided, for a commercial game | `measures`: per-frame values of the mapped measures (Mario's x, speeds, an enemy's state, the score counter) as read from the original's RAM | They are few named numbers, not memory dumps, and Gym Retro published more (whole savestates). But they are "memory contents" under the M1.1 rule, and the rule should be changed on purpose, not by a data set. Little is lost: anyone with the ROM makes them again from the recipe, and `curve_original` lets them check they got the same |
| Shareable, for an open game | Everything, measures included, for Moss Hop and originals made in Game Printer | We own the source game |
| Never | ROMs; patched ROMs; frames, screenshots and video; sprites, tiles, palettes and nametables; level data lifted from the ROM; music and sound; emulator snapshots and checkpoints; RAM, PPU or APU dumps; disassemblies; any slice of a non-commercial-licensed data set such as TheGreatRambler's Mario Maker 2 dumps (CC BY-NC-SA 4.0) | AGENTS.md, "Never commit", and the licences |

So a published data set for Super Mario Bros. is recipe-first: `clips`, `events`, `splits`, `windows` and `scores`, with `measures` left out and a line in the card saying `gp dataset materialize` makes it from your ROM. Frames for a world model are made the same way, by `gp video` on the user's machine.

Recommendation: keep `measures` local for commercial games as the default, and file the question for the user (and legal advice) rather than decide it here (the open-questions row this report adds).

## 4. An open source workflow instead of patches

### Two kinds of content

| Content | Where it comes from | How it's shared |
|---|---|---|
| Made for Game Printer: new levels, model changes, profiles, clips, themes, original sprites, sounds | Its author | A plain source repo: text files that diff in git, forks, pull requests and review, under the author's license. No IPS or BPS patch for anything that doesn't come from the ROM |
| The base game's copyrighted parts: Nintendo's graphics, music and original level data | The player's own ROM, at print time, through the asset map | Never shared. The repo pins the ROM's SHA-256 (`template.toml`'s `source.accepts`) and the asset map's hash; `gp template extract` lifts them into `$GP_HOME/work/` |

This is already how a template works: `model.toml` names each slot's recipe and holds nothing, and the asset map fills it from an accepted ROM (docs/templates.md). The open source workflow is that layout used as a project repo, for content that isn't the template's own.

### Existing hacks

A hack such as C4 Remastered starts as a base ROM plus an IPS patch. It comes in once:

1. `gp roms add --patch` (proposed in nes-kaizo.md) applies the patch to the user's ROM and registers the patched hash beside the base (nes-kaizo.md).
2. A diff scan sorts the patch's ranges into level data, art and code (`gp roms diff`, labelled by SMBDIS.ASM routine).
3. The hack's levels are lifted through the asset map like the base game's.

After that, only with the hack author's agreement, the levels can live as source files in a package repo, in the model's own level format. Their art stays in the patch if it is edited Nintendo art.

The legal line, which needs advice before anything is published:

| Part of a hack | Whose work | Can it be a source file in a public repo |
|---|---|---|
| Level layouts the hack author placed (where blocks, pits and enemies are) | The hack author's, built from the game's objects | Only with the author's permission, and even then it's a derivative of the game: Micro Star v. FormGen (9th Cir. 1998) held that player-made Duke Nukem 3D levels sold on a CD were derivative works that infringed, though the files only referenced the game's art, because they "incorporated the game's characters and story". Sharing free, non-commercial levels for a game the player must own is what the hack scene does; selling them is what the court stopped |
| New art drawn from scratch | The hack author's | Yes, under their license |
| Edited Nintendo graphics or music | Partly Nintendo's | No. It stays a patch applied to the player's ROM |
| Code changes | Usually small edits of Nintendo's code | No as code. As a model change (a profile option, a number) it's our text, written from the behaviour |

Lewis Galoob Toys v. Nintendo (9th Cir. 1992) is the other side: the Game Genie wasn't a derivative work because it didn't hold the game "in some concrete or permanent form". A patch applied at the player's end is close to that; a published file of levels is closer to Micro Star.

Precedent for levels living outside the ROM: Lunar Magic saves Super Mario World levels to `.mwl` files that hackers trade and import into another ROM; Moondust (PGE) reads and writes SMBX's open `.lvl` and `.lvlx` level files (PGE-File-Library-STL); Mario Maker courses are shared as Nintendo-hosted course IDs; decompilations extract assets from the player's ROM (`baserom.<VERSION>.z64`). The sharing etiquette of `.mwl` files wasn't found in a citable source.

### CI for a content repo (design)

There is no remote today, so this is local hooks first, with the same steps for a hosted runner later.

| Step | What runs | Needs |
|---|---|---|
| Layout | `gp package check` (section 5): required files, versions, nothing that must not be there | Nothing |
| Model | `gp model check` and `gp template check` | Nothing |
| Print | `gp template extract`, then a `gp print` (proposed) that builds the Bevy game from the extracted copy | The contributor's ROM, found in `$GP_ROM_DIR` by hash |
| Clips | `gp capture regenerate` (proposed in clip-set.md): make every clip in `clips.toml` from the ROM and compare each `curve` | The ROM |
| Scores | Score every kept clip; write a score record into `evidence/` (section 8) | The ROM |
| Difficulty | `gp level difficulty` for each changed level, posted as a PR comment (the heat strip and the total) | Nothing: it runs on the model |

Locally, a `pre-push` hook (opt-in, like `.githooks/pre-commit`) runs them. On a hosted runner there is no ROM, so the runner does the steps that need none (layout, model, difficulty) and checks the steps that do through records: a contributor's signed score record for the PR's model hash, reproduced by a maintainer (section 8). That keeps every ROM on someone's own machine.

### Against the hack scene's workflow today

| | Patches (SMB Arena, romhacking.net) | A Game Printer package repo |
|---|---|---|
| Finding a hack | SMB Arena's 3,735 SMB1 hacks with tags and downloads; romhacking.net, read-only since 2024-08-01 (nes-kaizo.md) | A repo with a card: tags, the base game's hash, difficulty, how exact it is. Searchable on a forge or the Hub |
| Seeing what changed | A binary patch; a diff needs both ROMs and a tool | `git diff` of levels and model text |
| Working together | One author; another's change is a second patch that may not stack (GreatEd's MMC3 builds break other patches) | Forks and pull requests; profiles let changes coexist |
| Versions | File names and readme dates | A package version and a model hash; score records per version |
| Credit and license | A readme, sometimes | `LICENSE`, the card's authors, `inspired_by` for borrowed mechanics |
| Trust | Players' reports | Clip curves checked against the original, signed records |

A modern audience expects GitHub-style repos, a version that means something, a README that is a dataset or package card, and a one-line install. The patch scene has none of these and works well for what it does. The package repo adds them without asking anyone to give up the original ROM.

## 5. A repo layout spec

Bevy doesn't cover it. Bevy is the engine the printed project runs on, and its one convention is an `assets/` folder in a Cargo project. Nothing in it describes models, mappings, levels, clips, evidence, ROM recipes or profiles, and the generated Bevy project is output that gets printed, not source.

The template directory (`templates/<game>/`, manifest `template.toml`, format 0.1.1) is already most of a package. The draft adds what a content repo needs, as package format 0.1.0:

| Path | Status | Holds |
|---|---|---|
| `gp-package.toml` | Required | The manifest: `format`, `id`, `version` (semver of the content), `title`, `authors`, `license`, and the template keys it extends (`[source]`, `[recipe]`, `[slots]`, `[ext]`, `inspired_by`). Today's `template.toml`, renamed or kept as an alias |
| `model.toml` | Required | The model; its canonical hash names every score |
| `mapping.toml` | Required for a model of a ROM | The state mapping |
| `fidelity.toml` | Required for a model of a ROM | The contract (tolerances) |
| `profiles.toml` | Optional | Physics profiles |
| `clips.toml` | Optional, required to publish evidence | The kept clips as recipes (clip-set.md) |
| `sources.toml` | Required | The ROM it prints from by SHA-256, and any patch by SHA-256 with its URL, author and permission note. Never the bytes |
| `levels/` | Optional | Levels made for Game Printer, one file a level, in the model's level format |
| `themes/` | Optional | Themes (`present` only) |
| `sprites/`, `sounds/` | Optional | Original art and sound by the package's authors, in the lifted formats |
| `ext/` | Optional | The Rust crate behind the model's `ext` hooks |
| `evidence/` | Optional | Score records by model hash (section 8), and their signatures |
| `README.md` | Required | The package card: what it is, the base game, how to print it, how exact it is |
| `LICENSE` | Required | The license of the package's own files |
| `NOTICE` | Required for a commercial base | It holds no part of the game; names and marks are their owners' (docs/open-questions.md, licensing notes) |
| `.gitignore` | Required | `print/`, `target/`, `*.nes`, `*.fds`, `*.sfc`, `*.ips`, `*.bps`, `*.state`, `*.png` outside `sprites/` |
| `print/` | Never committed | The printed Bevy project and web build |
| ROMs, patched ROMs, lifted assets, snapshots, recordings, frames | Never | As AGENTS.md says |

A patch file (`.ips`, `.bps`) isn't in the package: `sources.toml` names it by hash and URL, so the player fetches it from where its author put it, as TASVideos asks for hack runs.

`gp package check DIR` would extend `gp template check`: the required files are there and parse, each format version is one `gp` reads, the manifest's hashes match, `clips.toml` names the same ROM as `sources.toml`, every file in `evidence/` names a model hash and parses, and nothing in "Never" is present (the pre-commit hook's content checks, run on the directory).

Precedent borrowed:

| Precedent | Taken |
|---|---|
| Cargo (`Cargo.toml`, `src/`, `target/` ignored) | A manifest at the root, a fixed place for code, build output ignored |
| Hugging Face repos | `README.md` with YAML is the card; data files at known paths |
| Decompilations (sm64's `baserom.<VERSION>.z64`) | The ROM is the player's, named by version and hash, extracted at build time |
| SMBX episode folders, Lunar Magic `.mwl` | Levels as files of their own, apart from the engine |
| Godot and Bevy templates | Engine output stays generated; the package is the source |

## 6. The layers

| Layer | Holds | Made by | Where | Shared |
|---|---|---|---|---|
| Recipe | `clips.toml`, `sources.toml`, the model, mapping and contract (by hash), profiles, TAS movies by URL and hash, presses as spans | People and `gp capture prune` | Git | Yes |
| Materialized | Recordings, frame traces and events, snapshots, lifted assets, rendered frames and video, the score cache | `gp` from the user's ROM | `$GP_STORE`, `$GP_HOME/work/` | Never |
| Derived | `clips`, `measures`, `events`, `splits`, `scores`, `windows` tables, the card, Croissant and the score record | `gp dataset export` | An output directory; `evidence/` for records | Within section 3's line |

The recipe layer is the source of truth. Derived tables can be deleted and made again; a data set version is a recipe version plus the hashes of the tables it gives.

## 7. Schemas

Common rules for every table:

| Rule | Value |
|---|---|
| Frames | NTSC NES frames at 60.0988 Hz. `frame` counts from the clip's start; `start_frame` and `original_frame` count from power-on in the original |
| Places and speeds | The model's units: pixels for places, pixels a frame for speeds, as exact decimal text (`223.0625`). The original's 1/256 subpixels are the fraction (`frac` in the mapping). A `_f64` column beside it is for plotting only |
| Counters and states | Whole numbers; named states as text |
| Hashes | Lowercase hex. SHA-256 for ROMs, patches and files (as `sources/nes.toml` and Croissant use it); BLAKE3 for store objects and curves (as the store and the results key use it) |
| Keys | Given per table; `clip_id` joins every table to `clips` |
| Metadata in each Parquet file | `gp.dataset.format`, `gp.run`, `gp.model`, `gp.frame_rate_hz`, `gp.table`, `gp.key`, `gp.units` (JSON of each column's unit) |

### clips (key `clip_id`)

| Column | Type | Unit | Meaning |
|---|---|---|---|
| `clip_id` | string | | The clip's ID, stable for the same model and corpus (`gen.w1_1.start.t1.jump.hold15`) |
| `name` | string | | In plain words |
| `source` | string | | `played` or `generated` |
| `start_input` | string | | The recording or input log the start comes from |
| `start_frame` | int64 | frames | The original's frame the clip starts at |
| `frames` | int64 | frames | Frames it runs |
| `presses` | string | | Button spans, a JSON list (`["a@0-14"]`) |
| `presses_log_blake3` | string | | A played clip's input log by hash; null for a generated one |
| `exact` | bool | | Every measure within tolerance on every frame |
| `score` | int64 | splits | One a measure split on a frame |
| `measures_exact`, `measures` | int64 | count | Measures exact, of those compared |
| `together_permille` | int64 | 1/1000 | Frames together as a share of all measures' frames |
| `curve_original` | string | | BLAKE3 of the original's values of every measure on every frame: what a clip made again must give |
| `curve_model` | string | | The same for the model |
| `says` | string | | The score in words |

### measures (key `clip_id`, `frame`, `path`)

| Column | Type | Unit | Meaning |
|---|---|---|---|
| `clip_id` | string | | |

| `original`, `model` | string | model units | Exact decimal text; empty for a name |
| `original_f64`, `model_f64` | double | model units | For plotting; null for a name |
| `distance` | string | model units | How far apart |

### events (key `clip_id`, `body`, `game`, `frame`, `what`)

| Column | Type | Unit | Meaning |
|---|---|---|---|
| `clip_id` | string | | |
| `body` | string | | In words (`the second goomba`) |
| `kind` | string | | The model entity kind |
| `game` | string | | `original` or `model` |
| `frame` | int64 | frames | |
| `what` | string | | `turns left`, `is defeated` |

### splits (key `clip_id`, `track`)

| Column | Type | Unit | Meaning |
|---|---|---|---|
| `clip_id`, `track` | string | | The track is an entity kind, `camera` or `game` |

| Table | Key | Columns |
|---|---|---|
| `scores` (one row a clip scored on a model) | `clip_id`, `model`, `record` | `exact`, `score`, `first_frame`, `record` (the score record's ID): the history of a clip across model versions, from the ledger |
| `attempts` (a try at a section) | `session`, `attempt` | `level`, `from_x`, `to_x`, `frames`, `cleared`, `died_at_x`: the user's play from the unified player, the label difficulty.md wants to fit against. Private by default: it is a person's play |
| `windows` (one row an input of a searched run) | `level`, `run`, `input` | `frame`, `x`, `y`, `edge` (press or release), `early`, `late` (frames), `millibits`, `parts`: `gp level difficulty`'s output |
| `levels` | `level` | `name`, `millibits`, `sections` (the heat strip): one row a level |

## 8. Score records

### What a record is

Every set of results (a clip's score, the fidelity, a conformance run, a difficulty score) is a record tied to exactly what it tested. The results store already keys each score by everything it reads (docs/determinism.md, `crates/gp-cli/src/serve/results.rs`), and the ledger lists the results the queue used, in order, with no time, so two runs with different thread counts give the same ledger byte for byte.

| A record needs | In the results key today | Missing |
|---|---|---|
| Model hash and version | `model`, the canonical hash | The model's schema version beside it (it's in the text, so recoverable) |
| Mapping hash | Inside `settings` | Kept apart, so a reader sees it |
| `clips.toml` hash | No | Yes: the set the record covers |
| ROM hash | `rom`, BLAKE3 of the whole file | The headerless SHA-256 that `sources/` registers, so a renamed or re-headered copy gives the same record. The prototype writes both |
| Patch hash | No | Yes, for a hack |
| Profile or switch set | No; an applied profile changes the model text | Named, so "modern" and "retro" scores aren't confused |
| gp build | `build`, the hash of the binary | The binary's hash differs on every platform, so it can't be compared across testers. Add the version, the commit and whether the tree was dirty (the run manifest already has `git.commit` and `git.dirty`) |
| Runtime | No | `gp-interp` with `SCENARIO_VERSION`, or the generated Bevy build with its version, and the platform |
| Clip | `clip`, including the snapshot's bytes | A snapshot is local; the clip should be keyed by its recipe, which every tester has |

### Where records live

`evidence/<model-hash>/<record-id>.json` in the package, beside the model, so a model version ships with its evidence. One record a test run, its ID the SHA-256 of its canonical JSON. The data set card summarizes them (clips exact, fidelity, testers). A `scores` table (section 7) is the same records as rows, for querying many versions at once.

### The record's shape

An in-toto Statement v1: `_type` `https://in-toto.io/Statement/v1`, `subject` a list of digests, `predicateType` a URI, `predicate` anything. SLSA's provenance (`https://slsa.dev/provenance/v1`) is the same envelope for builds, with `buildDefinition.externalParameters`, `resolvedDependencies` and `runDetails.builder.id`. A score record borrows the envelope and not SLSA's fields, since it records a test, not a build.

What a "tested by X" record claims, in one sentence: these clips (by `clips.toml` hash and each clip's recipe hash), on this ROM (headerless SHA-256, and the patch's), with this model, mapping and contract (hashes), under this profile, run by this gp (version and commit) on this runtime and platform, gave these curve hashes and these scores.

```json
{
  "_type": "https://in-toto.io/Statement/v1",
  "subject": [{"name": "smb-side-by-side-2.clips", "digest": {"sha256": "b9da3868..."}}],
  "predicateType": "urn:game-printer:score-record:0",
  "predicate": {
    "rom": {"sha256": "fcb6a0ef...", "patch": null},
    "model": {"hash": "65440269...", "name": "smb1"},
    "mapping": {"hash": "e4ae48c4...", "schema": 13},
    "contract": "00b550ec...",
    "profile": null,
    "runtime": {"name": "gp-interp", "scenario": "0.4.0"},
    "gp": {"version": "0.1.0", "build": "f0871068...", "commit": null},
    "clips": [{"id": "gen.w1_1.start.t1.jump.hold15", "spec": "accbb133..."}],
    "results": {"clips": 169, "exact": 126, "errors": 0},
    "files": [{"path": "data/clips.parquet", "sha256": "b9da3868...", "rows": 169}]
  }
}
```

The prototype writes this as `record.json`, unsigned, with `null` where the build doesn't know the value yet.

### Re-verifying

Anyone with their own ROM checks a record without trusting the tester: check the ROM's hash against `rom.sha256`, regenerate every clip from `clips.toml` (`gp capture regenerate`), score them on the model the record names, and compare each curve hash and score. `gp capture verify` already does this for one machine's ledger: it recomputes each result from the stored model and a fresh cache and checks it hashes the same. A record's verify is the same check across machines.

### Signing (design only)

| Option | What it is | Fit |
|---|---|---|
| SSH signatures | `ssh-keygen -Y sign -n <namespace>` signs any file with an SSH key; `-Y verify` checks it against an allowed-signers file. Git signs commits and tags the same way (`gpg.format = ssh`, `gpg.ssh.allowedSignersFile`, "one or more lines of principals followed by an ssh public key") | Local-first, no new tool, keys people already have. Recommended now |
| minisign | "A dead simple tool to sign files", Ed25519, with a trusted comment that "cannot be modified without the secret key" | Good, but another tool and key to manage |
| Sigstore (cosign) | Keyless signing: Fulcio issues a short-lived certificate binding an ephemeral key to an OpenID Connect identity, and Rekor logs every signing. cosign signs blobs and in-toto attestations | For a hosted runner, where the signer is a CI identity. Needs the network and an identity provider |
| Gitsign | "Keyless Git signing using Sigstore" for commits | The same, for commits that add records |
| in-toto, SLSA | The statement format above, and provenance for builds | The record's envelope |

Recommendation: now, a record is signed with the tester's SSH key into `evidence/<model-hash>/<record-id>.json.sig`, under the namespace `game-printer-evidence`, and the package keeps `evidence/allowed_signers`. Commits that add records can be SSH-signed too. Later, a hosted runner signs with Sigstore keyless, and its records sit beside people's.

### Many testers

Reproducible builds define a build as one where "any party can recreate bit-by-bit identical copies" from the same inputs, verified "by bit-by-bit comparison". Game Printer's scores are built the same way: determinism makes a score a function of its inputs. So trust grows with agreement: a model version's card can say "reproduced by 3 testers on 2 platforms" when three signed records from different signers have the same subject and the same curve hashes. A record that disagrees with others on the same inputs is a determinism bug, and the conformance suite's business.

## 9. The card and Croissant

`gp dataset export` writes both. The card's YAML has the Hub's `configs` (one a table, `clips` the default), the license and tags. Its sections, after Datasheets and Data Cards:

| Section | Holds |
|---|---|
| What it is | The run, the format version, the sentence that it holds no game data |
| What it was made from | The score record's inputs as a table |
| Results | Clips scored, exact, failed |
| Tables | Each table's purpose, key, rows and columns with types and units |
| Load it | DuckDB, polars and `datasets` in a few lines |
| Files | Each file's SHA-256 and rows |
| Use and license | The sharing line for this game, the authors and credits (TAS authors with links), names and marks |
| Not yet written | Intended uses and known limits ("the model differs from the original on 43 clips; see `splits`") |

`croissant.json` has one FileObject a table (with `sha256`) and one RecordSet a table with its key and fields, conforming to Croissant 1.0. The Hub would generate its own from the Parquet once published; ours has the keys and descriptions it can't infer.

## 10. Versioning

| Thing | Version |
|---|---|
| The data set format | `DATASET_FORMAT`, 0.1.0: the tables and columns. A column added is minor; one removed or changed in meaning is major. Written in every Parquet file's metadata |
| A data set | Its content ID: the SHA-256 of the score record, which names the model, mapping, contract, ROM, patch, clip set, gp and runtime, and every file's hash. Two exports of the same inputs give the same ID (measured: identical bytes twice on SMB1) |
| A package | Semver of its content in `gp-package.toml`, and the model hash per version |
| The changelog | `CHANGELOG.md` in the package: each version's model hash, clips added and dropped, records added. `gp` can draft it from two records |

Files are content-addressed through the record: a file's name is stable (`data/clips.parquet`) and its hash is in the record and the card. A published copy can use the hash in its path for caching.

## 11. Licenses

| Content | Recommended |
|---|---|
| Recipes, model text, mappings, records, tables of our own scores | CC0 for data, or the repo's Apache-2.0 for the text. CC0 waives every right, which is what a reference data set wants |
| Tables with TAS-derived presses | CC BY 4.0 for the set, with each movie's authors, link and tool-assisted label, as TASVideos' CC BY 2.0 asks |
| A package's own levels and art | The author's choice; the package's `LICENSE` |
| Anything mixed with a CC BY-NC-SA set (Mario Maker 2 dumps) | Not shareable; local fits only, as difficulty.md says |

ODbL's share-alike would bind people who build on the tables; there's no reason to ask that of them.

## 12. Loaders, publishing and management

### Loaders

```python
import duckdb
duckdb.sql("SELECT path, count(*) FROM 'data/measures.parquet' WHERE original <> model GROUP BY path ORDER BY 2 DESC").show()

import polars as pl
clips = pl.read_parquet("data/clips.parquet").filter(pl.col("exact").not_())

from datasets import load_dataset
measures = load_dataset("parquet", data_files="data/measures.parquet")["train"]
```

No Python package of ours is needed while the tables are plain Parquet; a tiny `gp-datasets` package would only add the units and a `materialize()` that calls `gp`. For the web editor, DuckDB-Wasm or a Parquet reader in TypeScript reads the same files; JSON from `gp --json` is enough until the editor needs more.

### Publishing

| Where | What could go there | Allowed today |
|---|---|---|
| Hugging Face dataset repo | The recipe-first set: `clips`, `events`, `splits`, the card, Croissant, records. For Moss Hop and originals, `measures` too | Nothing is published: everything is local, with no remote (AGENTS.md). The design is ready for when the user asks |
| A release on a forge | A packed package with its evidence | Same |
| Our own site | The card rendered, records and their signers, a viewer | Same; `site/` builds only docs today |

### Management

| Thing | Maps to |
|---|---|
| A run (`smb-side-by-side-2`) | A working data set: export it any time; nothing is versioned until a set is kept |
| Kept clips (`gp capture prune --apply`) | `clips.toml` in the package: the recipe of the next data set version |
| Skipped clips | Marked `skipped` in the strip, so they leave the pool and the next export; never deleted (clip-set.md) |
| Agents' work (`agent/<n>/attempt.json`, the ledger) | Records for the model versions they produced; an attempt that merges gets its record in `evidence/` |
| Retention | Records are small and kept for every released model version. The score cache and materialized data can be dropped and made again (`gp store gc` for the store). Exports are scratch |
| A community clip | A pull request adding recipes to `clips.toml`. Review runs `gp capture regenerate` from the reviewer's ROM: the curve hashes must match the contributor's, and the prune says what the clip holds that the set doesn't, so the reviewer decides by coverage |

The clip `gen.w1_1.start.t1.jump.hold15`, "World 1-1: jump, held 15 frames", from the export of `smb-side-by-side-2` on 2026-10-30 (its pool had 169 clips that day).

## 14. The prototype

`gp dataset export --run R --out DIR [--format parquet|csv]` scores every clip in the run's pool on its model, as `gp capture prune` does, and writes:

| File | What |
|---|---|
| `data/clips.parquet`, `measures`, `events`, `splits` | The four tables of section 7, uncompressed, one row group each, with the metadata keys |
| `README.md` | The card, with the Hub's YAML |
| `croissant.json` | Croissant 1.0 |
| `record.json` | The score record, an unsigned in-toto statement |

It writes nothing in the run (the score cache goes to `$GP_HOME/work/dataset/<run>/`) and nothing anywhere but `--out`.

| Measure | Value |
|---|---|
| `smb-side-by-side-2`, release build, 8 jobs, scratch `GP_HOME` with the run cloned and the real store read only | 24 s; 169 clips, 126 exact; 169, 519,362, 927 and 73 rows; 55 KB, 1.8 MB, 9 KB and 13 KB |
| The same export twice | The same bytes |
| Moss Hop test | `crates/gp-cli/tests/dataset.rs`: builds Moss Hop, starts a run, makes the tool's clips, exports, opens every table with the `parquet` reader and checks rows against the record, the card's configs, Croissant's record sets, the same files twice, and CSV |

The dependency is `parquet = "=60.1.0"` with `default-features = false`: the low-level column writer, with no Arrow and no compression codecs. It added 16 packages to `Cargo.lock` (`ahash`, `half`, `num-bigint`, `num-integer`, `twox-hash`, `seq-macro`, `libm`, `const-random` and their build helpers, and a newer `getrandom`), all downloaded through cargo. Compression is off so the bytes are stable and the code small; zstd is a feature away when sizes matter.

What it doesn't do yet: `measures` aren't held back for a commercial game (the export is local, so the line applies when publishing), the record has no commit or profile, there's no `materialize`, `scores`, `windows` or `attempts` table, and it covers the pool only, not clips waiting on `requires`.

## Open questions

- May per-frame measures of a commercial game be shared? Default: no; keep them local and publish recipes and curve hashes, until the user decides with legal advice (docs/open-questions.md).
- Package format: rename `template.toml` to `gp-package.toml`, or extend it? Default: extend `template.toml` to format 0.2.0 with `version`, `authors` and `license`, and add `sources.toml`, `clips.toml` and `evidence/`.
- The results key's portability: key a clip by its recipe and the ROM by its headerless SHA-256, and add a portable build ID (version and commit)? Default: yes for records; the local cache key can stay as it is.
- Signing: SSH signatures now? Default: yes, design only until a second tester exists.
