# Per-frame CPU work

> Brought from game-printer with wave 3b of the port: `gp cycles` and its five subcommands are in gameprinter over the gp-cycles crate. The measurements below are game-printer's (workers rngH to rngH5, 2026-11-03 and 04); the hooks they name are Donkey Kong's in the games checkout (`games/donkey-kong/ext/src`), where game-printer had `templates/donkey-kong-oe/ext/src`. The input flags (`--input`, `--baseline`, `--recording`) read a recording from gameprinter's store.


Some games step a random generator once per pass of the loop the CPU idles in while it waits for the next frame. Donkey Kong's idle loop at $C7E1 calls $F4ED, which shifts the 64-bit register $18-$1F once, and the frame's spare time decides how many passes fit: 67 to 369 in the user's play. Ngo and Williams, "Entropy Lost" (PCG Workshop 2022), describe the same register and its effective period of 32,767. A model that steps its generator as the game does (the retro side of the `rng_per_frame` switch) needs the frame's work in cycles. This page is how `gp cycles` measures it. None of it runs in a rebuild.

## What decides the count

From the traces of the user's play (6000 frames) and run 5658S (5000 frames):

| Part | Rule |
|---|---|
| A pass | 76 cycles when bit 1 of $18 equals bit 1 of $19, else 77 (the BEQ and SEC at $F4FA, then eight RORs) |
| The frame | The vblank grid: 89342 PPU dots a frame, 89341 on an odd frame whose pre-render line has rendering on ($2001 bits 3 and 4) |
| The NMI | Taken after the instruction the vblank falls in, if it falls before that instruction's last cycle, else after the next one; its entry is 7 cycles after |
| The handler | The cycles of the game's code on the frame's RAM, the OAM DMA's 513 or 514 included |
| The count | The passes that start more than 7 cycles before the next NMI's entry |

Given the frame's RAM, these give the count exactly: `gp cycles chain`, keeping its own $18-$1F and taking the rest of RAM from the trace each frame, matches every frame of both runs, and its random bytes never differ from the game's.

## Commands

| Command | What it does |
|---|---|
| `gp cycles slice --rom ROM` | Writes the cartridge's program to $GP_HOME/work/cycles/<ROM's blake3>/ for gp-cycles to run. Mapper 0 only. Nothing of it goes in the repo |
| `gp cycles readset ROUTINE` | Each call's cycles and the RAM it reads before writing (not the stack). No ambiguous read-state means the cost is a function of those bytes |
| `gp cycles check ROUTINE...` | Each call against gp-cycles' cost on the RAM, registers and controller at the call |
| `gp cycles chain --idle PC --keep LO-HI` | The CPU on its own across frames, as above |
| `gp cycles chain ... --mapping FILE --known LIST` | The same with only the bytes the model holds taken from the original each frame (a state mapping's `ram` bytes and `LIST`, hex `lo-hi` entries or `@FILE`); every other byte stays at its value at the run's first frame. The count of exact frames is how much of the frame's work the model's state decides |
| `gp cycles chain ... --resync` | Each frame from the original's NMI entry, registers, the stack above S (the NMI's pushed status and return address, which say where in the idle loop the frame resumes) and kept bytes, so a wrong count doesn't carry into the next frame |
| `gp cycles split --out FILE` | Each frame's handler cycles from its entry to its RTI, and the cycles of each routine it calls at any depth, callees included: one JSON line a frame, for finding which routines move the frame's cost. A routine left by pulling its return address (Donkey Kong's $E0F1, PLA PLA at $E107, then an RTS to its caller's caller) ends at that RTS with its caller; before 2026-11-04 such a frame read as no handler (956 of 79,403 corpus frames, a barrel at a ladder's top), its callers uncounted |
| `gp cycles split ... --pcs FILE --ram-out FILE` | The same with each frame's instructions (every address the handler ran, its runs and their cycles, a branch's taken cycle and a page crossing's included) and the RAM at the NMI's entry, for finding the branches that move a routine's cost and the bytes they read. Game data: keep both under $GP_HOME/work |
| `gp clip score ... --values PATH` | A clip's per-frame values of a mapped path straight through, the original's and the model's, in `values.json` with the frame pairing: with a probe mapping that compares `counters.frame_cost` and `counters.random`, the model's cost each frame beside the original's |
| `gp cycles chain ... --ram-out FILE` | The original's RAM at each NMI entry, 2048 bytes a frame, for checking a model of a routine's state offline. Game data: keep it under $GP_HOME/work |

### On an arcade romset

Given a MAME zip as `--rom`, the commands read the main Z80 from gp-arcade's
instruction trace and access log (crate::cycles_z80):

- `slice` writes the main CPU's ROM.
- A call is a `call` or `rst` to the routine, ended by the first instruction
  whose stack pointer is back at the caller's. An interrupt the board takes
  inside a call (Tapper's game loop runs with interrupts on) is left out of
  its cycles and its reads, the acknowledge's 19 cycles in mode 2 included.
- `readset` reads work RAM (E000-E7FF); the stack's accesses are left out by
  the instruction that made them.
- `check` runs each call alone on gp-arcade's own Z80 (MAME's), from the
  frame's start state with the frame's writes before the call, the call's
  registers from the trace (the refresh register too, which `ld a,r` reads),
  and the ports as the frame read them. Tapper, frames 2000 to 4000 of a
  five-level run: 0325, 0379, 03EA and 5CED (the handler's) 2001 of 2001
  calls exact each, the random routine 5FAC 95 of 95, its only RAM read E390
  (its cost varies with R).
- `split` takes the frame's first interrupt (the CTC's) as the handler, to the
  first instruction back above its return address; `--ram-out` is work RAM at
  the handler's entry.
- `chain` reports the original's idle-loop passes a frame (Tapper's loop at
  60F8, `ld a,(e16c); cp 1; jr c`, about 3,850 a frame) and doesn't predict
  them: the board's interrupt comes from its CTC counting the video timing,
  which a Z80 run alone doesn't model.

## How much the model's state decides

`--known` with `--resync` scores a group of bytes on its own: hold the group at its first value and give the rest from the original, and the frames that stay exact are the ones the group doesn't move. On frames 1200 to 7200 of the user's play (recording ad8352d8c24f, 6001 frames):

| Bytes the original gives | Exact frames |
|---|---|
| All of RAM | 6001 |
| All but the sound driver's 27 and $E4-$EB | 2693 |
| All but the barrels' tiles $72-$76 and $5A-$5D | 5398 |
| Only the mapping's 45 and $18-$1F | 47 |

## The cost model

The rebuild runs no original code, so the model declares the handler's cost as terms over its own state (core feature `cost.frame`, docs/model.md, "Rules and counters"): a base, and each term's cycles on a frame its tests hold (a counter as the frame started or as it ends, an action held this frame or the last, a machine's state, a count of bodies). A hook that runs a routine of the original's adds the cycles of the branches it took (`ExtCx::add_cycles`). The `dk_idle` hook reads the sum (`ExtCx::frame_cycles`), adds the OAM DMA's extra cycle when the CPU cycle's parity at the NMI's entry says so (it carries the parity from frame to frame, bit 1 of `ext[2]`; the parity that makes the DMA 514 is `ext_params.dma_parity`), and steps the register in what is left. The model's cost each frame is the counter `frame_cost`.

What the handler's cost depends on, from `gp cycles split --pcs --ram-out` on the corpus (111 clips, 79,058 frames with no NMI inside a frame's work; worker rngH, 2026-11-03):

| Routine | Frames it varies on | What decides it | In the model |
|---|---|---|---|
| The handler's own code, $C85F-$C8F2 | Every frame | The dispatch on $4E, $4F, $9A, $55 and $0505, and the OAM DMA's 513 or 514 (the write's CPU cycle parity, 50% each) | The DMA by the hook, from the CPU cycle's parity at the NMI's entry (514 on an odd cycle of gp-nes's count: `ext_params.dma_parity = 1`, from the handler's own cycles against `nmi.cpu.cycles` on walk clip 1, 351 of 352 frames); the dispatch as the base and the `playing` term |
| The controller, $F50E | 18% | A held now and the last frame (5 or 6), a direction held both frames ($F552, 9), for each controller | Terms on `pad` (controller 1 as pressed, feature `cost.frame_pad`) and `held_before` ($15 the last frame, the keep_direction view): exact on 78,902 of 79,058 frames over the RAM (the rest read controller 2). `held` was the keep_direction view and the demo's held actions, which aren't the pad the routine reads. $F552's 9 cycles come once for any overlap; the terms count each direction, so two directions held through are 9 too many |
| The timers, $F4AC | 64% | Each timer $35-$3E above 0 when it runs (5 each), and on a divider wrap $3F-$45 too (90 more); in play it runs after the frame's work, so a timer the frame set counts | Terms on the counters at the frame's end, and from 1 to 0: exact on 76,891 of 76,918 frames over the RAM. $35 is the title's `select_wait` (64 when Select moves the cursor, $C966, nonzero on 803 of 79,403 corpus frames); $3C-$3E are 0 on every corpus frame |
| The sound driver, $FA48 | 91% off its commonest value (262 values) | A function of the driver's 27 bytes and bit 3 of $18 (79,058 of 79,058 frames, 27,016 states), all model state the dk_sound hook keeps | The dk_sound hook adds each branch's cycles as it steps the driver (`Sound::step_cost`): exact on 79,355 of 79,355 corpus frames against `gp cycles split` (the test `driver_cycles_match_the_split`, run by hand on a split's RAM and the program from `gp cycles slice`) |
| The PPU buffer, $F228 | 2.6% | The writes the game queued at $0331 the frame before (15 lengths) | Not yet |
| The stage, title and demo routines $CAC9, $C8F3, $CA30, $F23C | Off play: 2 in 5 to 3 in 5 | The scene's script byte $43, $53 and the timers; a screen drawn now and then (8000 to 15,600) | Not yet |
| The play routine, $CE7C | Every play frame (6188 values) | 872 independent counts of basic blocks over the game, most of them here: the box tests $EFEF (two boxes' four comparisons, early out), their callers' loops over barrels and fires, Mario's state, sprite writes | Its median (the `playing` term), less what the dk_idle hook costs branch by branch over model state (`ext/src/play.rs`, below) |

The cost is exact on a frame only when every routine's is, so the count stays wrong on almost every frame until the sound driver and the play routine are modelled branch by branch. Measured in the model (`gp clip score --values`, the probe mapping, every corpus clip straight through with the original's draws): see "Where the switch stands".

## Costs from the ROM's code

Since worker rngR (2026-11-04) no hook counts a routine's cycles by hand. A routine's cycles along a path are a fact about the ROM's code, so they are read from the person's ROM (core feature `cost.code_walk`):

| Part | What |
|---|---|
| The recipe | The asset map lifts the program's code as tables: Donkey Kong JU's `code_c500` ($C500-$C60C), `code_c6a3` ($C6A6-$C702) and on round 100m's hammer palette, its ending's palette and fallen Kong's poses as `code_c707`, `code_c735` and `code_c74e` to $F55A (cut as Original Edition's map cuts them since 2026-11-07; before, one span from $C6A3, which the hooks placed at $C6A6) and `code_fa45` ($FA45-$FAE4), the rest of $C000-$FFFF being the tables, pictures and sound data the map already lifts (Original Edition's from PRG $4500 on, its $C000 bank). The lifted files' digest is pinned (`recipe.lifted_sha256`). The model names the tables in the hooks' entities' `ext_tables` |
| The walker | `gp_cycles::walk` reads the code from the lift by CPU address, from a routine's first instruction to its RTS (an RTS after two pulls returns from the caller, as $E0F1 does), and adds each instruction's cycles, a taken branch's 1 and 1 more to another page, and an indexed read's 1 when it crosses a page. At each conditional branch it asks the path which way it goes; at an indexed read that can cross a page, the index (and for (zp),Y the pointer); at a JSR or JMP, whether it is costed as a measured fact |
| The path | The hook's [`Route`](games/donkey-kong/ext/src/play_mario.rs in the games checkout): as the hook steps the routine's behaviour over model state, it queues each branch's outcome by the branch's address, in the order the code meets it, and the measured costs by the JSR's or JMP's address. A walk that meets a branch with no answer, or leaves an answer unused, gives no cost, so a path that strays from what the model decided shows as no cost instead of a wrong one |
| Measured facts | The metasprite writer $F096 at 2 by 2: 593, mirrored 705 (from its JSR or JMP to its RTS); $F082 and $F088, which reach it by a branch, 598 and 710 from their JMP; $F080 601; the hides $F08E 270 and $F092 337; the hammer's own sprite by its way, 405 and 465 up, 423 and 501 down |
| Without code | An original with no such code (as Rivet Rodeo's empty `code_*` slots were) gets no walk: the routines keep the cost terms' medians, and the sound driver adds 0 |

The walks equal the hand counts they replace on every split test (`gp cycles split` RAM, run by hand with `GP_PLAY_SPLIT` and `GP_PLAY_PRG`): the barrels 49,240 of 49,245 25m play frames, the fires 49,473 of 49,480, Mario 49,042 of 49,045, the touch tests 51,996 of 51,996, the pad 47,471, Pauline and the drum 52,060, and the sound driver 79,355 of 79,355 (`GP_SOUND_SPLIT`). Three of the old measured draws had absorbed hand-count errors, which the walk found: $E0AE's dispatch was 2 cycles low on every path (the roll's draw read 603, its own 601), the fire's climb 3 low (its draw read 713, $F088's 710), and the jump's arc $EF72 takes its start path on the takeoff's frame ($042C still 0), 1 fewer, which the takeoff's draw had held.

## The NMI's place at a clip's start

The idle loop's count needs, at a clip's first frame, where the NMI stopped the loop, the carry it pushed, its entry's dot after the vblank, the CPU cycle's parity at the entry (the DMA) and whether the frame is odd. No RAM byte the mapping reads holds them, so the mapping reads them from the console as it takes the NMI (feature `field.machine`, gp-nes's `nmi.return_pc`, `nmi.status`, `nmi.vblank_dots`, `nmi.cpu.cycles` and `nmi.ppu.odd_frame`, docs/runtime-protocol.md) into the counters `nmi_resume`, `nmi_carry`, `nmi_entry`, `nmi_cycle_odd` and `frame_odd`, which the dk_idle hook keeps from frame to frame. Loaded, not compared. On walk clip 1 the hook's entries from the original's handler cycles are the console's (33, 26, 27, 26, 36, 29, 27 from original frame 4582), and the frame's parity is `ppu.odd_frame` at the entry.

A pass the NMI stops after its STA $00 ($F4F1) and before its EOR $00 ($F4F7) goes on with $00 as the handler leaves it: the handler stores there ($C875, the sound driver's $FA72, many play routines), so the EOR compares bit 1 of $19 with that byte, not with bit 1 of $18. It is about one frame in ten. The hook takes the counter `scratch_00`: the sound driver's $06F0 top two bits ($FA72), or a value that is neither 0 nor 2 while the play routine runs unpaused, whose stores there were never 0 or 2 on 30 sampled corpus clips (193 such frames). Run on the original's handler cycles (a Python copy of the hook over the split's RAM, worker rngH2), a clip's register then matches straight through until the first frame whose handler overran (no cycles in the split) or where the rule fails: 470 frames on clear-25m clip 2 (to original frame 1642, a stage frame), 251 on climb-ladder clip 8, 223 on barrels clip 8, 215 on fall-too-far clip 1; without the $00 rule, 4 frames on walk clip 1 and 3 on barrels clip 1. The rule's misses: a death's frames that run the play routine but store nothing there (the model's `dying` state isn't `playing`, so these are covered), and frames whose stores leave 0 or 2.

## The model

The rebuild runs no original code. The bytes the frame's code reads, 279 in Donkey Kong's 25m, become model state, each listed with its effect on the cycles, and the retro switch steps the generator by a cost function over that state. `chain` measures the exact rate as each group of bytes lands.

## Where the switch stands (2026-11-03, worker rng)

The register and both sides of the switch are model state and code; the retro side's count is not the game's yet, since the handler's cost isn't computed from model state.

| Part | State |
|---|---|
| The generator as model state | Done: the counter `random` holds $18-$1F, $18 the top byte (mapping `counters.random`, 8 addresses, feature `field.whole_64`, not compared: `presentation = true`). | The draws | Done: with no draws script, or none at the site, the hooks read the register as the game does: $19 for the ladder choice and a roll-off, $19 plus the fire's slot for a fire's way ($E2DD), through `ExtCx::scripted_draw` |
| The idle loop | Done: the `dk_idle` hook (entity `idle`, core `entity.hook_last`) runs the loop's 20 instructions on the register from where the last NMI stopped them to where the next stops them, on the vblank grid (89342 dots, 89341 on an odd frame with rendering on), the NMI after the instruction its vblank falls in and 7 cycles to its entry, keeping a ROR sequence the NMI cut and its carry |
| The handler's cost from model state | Started (worker rngH, 2026-11-03): the model's `[cost]` (core `cost.frame`, "The cost model") with the controller's and the timers' branches as terms and medians for the rest, and the DMA's parity carried by the hook. `ext_params.handler`, the median 10207, is what a model without `[cost]` takes |
| The normal side | Done: the switch `rng_per_frame` (in the preset `normal`) removes `idle_loop`, and the register steps once a frame |
| The frame_overrun lag switch | Not started: it needs the handler's cost too. In the user's play the handler takes 0 to 24634 cycles of a frame's 29780, so no frame overruns there |
